# notux: процессы, ФС и что было сломано

Этот файл — отчёт о том, что сделано в текущем раунде работы над ядром:
пункты 3, 4 и 4.5 из плана (zombie/wait4, наследование fd, архитектура
папок), плюс разбор и исправление твоей старой "херни с файловой
системой". Плюс справочник по API, чтобы не лазить по исходникам
каждый раз.

## TL;DR — что изменилось

1. **Процессы теперь не исчезают молча после exit.** Есть zombie-состояние
   и `wait4()`, через который родитель может забрать код возврата ребёнка.
2. **fd 0/1/2 наследуются через execve.** Можно открыть файл, сделать
   `dup2()` на fd 1, запустить дочерний процесс — и он будет писать в
   этот файл, даже не подозревая об этом.
3. **Нашёл и реально запустил твою файловую систему.** До этого
   раунда у `xv6fs` физически не было инструмента, который мог бы
   создать корректный образ диска — поэтому она никогда и не
   монтировалась по-настоящему на реальном диске. Плюс в AHCI-драйвере
   был баг, из-за которого чтение/запись диска либо зависало, либо
   "работало" по случайности оптимизатора. Оба бага исправлены,
   проверено множеством прогонов в QEMU с реальным diск-образом.
4. **Нашёл и исправил системный баг планировщика**, из-за которого
   переключение между двумя процессами (не один процесс — именно
   переключение туда и обратно) гарантированно ломало состояние
   второго процесса. Это была главная причина, почему `wait4()`
   изначально не работал — не логическая ошибка в `wait4()` самом по
   себе, а в том, что к моменту его вызова память родителя была уже
   затёрта. Подробности ниже, это самое интересное.

## Архитектура папок (пункт 4.5)

Ничего сложного не стал городить — xv6fs и так уже умеет директории,
просто раньше ими никто не пользовался. При монтировании ФС (в
`kernel/onion.c`, `create_default_dirs()`) гарантированно создаются:

```
/            корень
/bin         исполняемые файлы (туда kладётся /bin/child в тестовом образе)
/etc         конфиги и логи рантайма (например /etc/result.log)
/root        домашняя директория root'а
```

Функция идемпотентна — вызывается при каждой загрузке, но не плодит
дубликаты (проверяет `dirlookup` перед `mkdir`). Это не "окончательная"
архитектура ФС, а минимальный скелет, чтобы было куда класть daemon'ы
и их логи уже сейчас. Расширять (`/var`, `/dev` и т.п.) — когда
появится конкретная нужда, не раньше.

## Процессы: zombie + wait4() (пункт 3)

### Что было

`exit_current_process()` сразу переводил слот процесса в
`PROCESS_STATE_TERMINATED` и слот становился свободным. Это значит: как
только процесс завершался, узнать его код возврата было уже нельзя —
данные стирались раньше, чем кто-либо успевал их прочитать.

### Что стало

`kernel/process.h`:

```c
typedef enum {
    PROCESS_STATE_READY = 0,
    PROCESS_STATE_RUNNING,
    PROCESS_STATE_ZOMBIE,       /* новое: процесс завершился, но ждёт reap */
    PROCESS_STATE_TERMINATED    /* слот свободен */
} process_state_t;
```

`process_t` получил поля:

```c
uint32_t ppid;       /* кто родитель (0 — родителя нет, это init) */
int      exit_code;  /* код возврата, хранится, пока не заберут */
```

`exit_current_process(int exit_code)` (`kernel/process.c`) теперь не
стирает процесс, а переводит его в `PROCESS_STATE_ZOMBIE` и
сохраняет `exit_code`. Слот навсегда остаётся занятым, пока кто-то не
заберёт зомби через `wait4()`.

**Известное ограничение (сознательно, не бага):** если родитель сам
умирает раньше, чем успевает подождать ребёнка — ребёнок (или сам
родитель) остаётся zombie навсегда, слот не освобождается. В POSIX
такого ребёнка усыновляет init и потом reap'ает. У нас такого
усыновления пока нет — следующий разумный шаг, если понадобится
переживающие родителя daemon'ы.

### Новый syscall: `wait4`

Номер **61**. Сигнатура (как в POSIX, но сильно урезано):

```c
long wait4(int pid, int *status, int options, void *rusage);
```

Реально используются только `status` (arg2 = rsi). `pid`, `options`,
`rusage` **игнорируются** — всегда ждём первого попавшегося zombie-ребёнка
вызывающего процесса, сколько бы их ни было.

**Главное: это неблокирующий вызов.** Если на момент вызова нет ни
одного zombie-ребёнка — тут же возвращается `-1`, без усыпления
процесса. Хочешь ждать — вызывай в цикле. Блокирующий `wait()` требует
нового состояния процесса `PROCESS_STATE_WAITING` и поддержки в
`schedule()` для адресного "разбудить вот этот процесс" — этого пока
нет, оставлено на будущее осознанно (см. раздел "Что не делал").

Возврат:
- `>0` — pid забранного zombie-ребёнка, `*status` заполнен его
  `exit_code`
- `-1` — подходящих zombie-детей сейчас нет

Пример из `user.c` (наш тестовый init):

```c
int status = -1;
long reaped = -1;
for (long tries = 0; tries < 10000000 && reaped < 0; tries++) {
    reaped = sys_wait4(&status);
}
/* reaped == pid ребёнка, status == его exit code */
```

Да, busy-loop — это специально для теста (10 млн попыток с запасом).
Для настоящего init'а это не годится, там нужен нормальный yield/sleep
между попытками — но раз блокирующего wait нет, ничего лучше спин-лупа
пока предложить не могу без доделки планировщика.

## Наследование fd 0/1/2 через execve (пункт 4)

### Проблема, которую решаем

У нас нет `fork()` — есть только "создать новый процесс и загрузить в
него ELF" (`execve`, syscall 59, `spawn_from_xv6fs()` в
`kernel/syscall.c`). Без доп. работы любой новый процесс всегда
получает чистый `ofiles[]` — то есть всегда разговаривает с
клавиатурой/экраном, и никак нельзя перенаправить его вывод в файл.
Для демона это самоубийство: ему либо нужен лог-файл, либо надо
молчать.

### Решение

При успешном `execve` (`spawn_from_xv6fs()`), после создания нового
процесса, но до переключения на него, делаем:

```c
process_t *caller = get_current_process();  /* тот, кто вызвал execve */
for (int fd = 0; fd < 3; fd++) {
    if (caller->ofiles[fd].ip) {
        idup(caller->ofiles[fd].ip);        /* inc refcount инода */
        child->ofiles[fd] = caller->ofiles[fd];
    }
}
```

Копируются **только fd 0/1/2** (не вся таблица) — осознанно, это не
`fork()`, это "у нового процесса такое же stdio, как у того, кто его
запустил", минимум, который нужен для демона с логом.

### Новый syscall: `dup2`

Номер **33**. `long dup2(int oldfd, int newfd)`.

Как обычно — делает `newfd` указывать на тот же inode, что и `oldfd`
(с `idup()`/`iput()` правильным рефкаунтом), можно потом закрыть
`oldfd`. Используется вот так (из `user.c`):

```c
long fd = sys_open("/etc/result.log", O_WRONLY | O_CREAT | O_TRUNC);
sys_dup2((int)fd, 1);   /* fd 1 теперь смотрит туда же, что и fd */
sys_close((int)fd);     /* лишний хэндл больше не нужен */
sys_execve("/bin/child"); /* ребёнок унаследует fd 1 = тот самый файл */
```

Заодно поправил `close` (syscall 3) — раньше можно было закрывать
только `fd >= 3`, теперь можно закрывать и 0/1/2, раз они теперь тоже
могут быть "настоящими" файлами, а не всегда железной
клавиатурой/экраном.

## Самое важное: баг планировщика, из-за которого ничего не работало

Это тот самый баг, который, скорее всего, стоит за твоей старой фразой
"нет процессов, что-то с ними не так" — он не в коде `wait4()` или
`dup2()`, он глубже, в том, как вообще переключаются процессы.

### Симптом

Тестовый сценарий: init открывает лог, редиректит stdout, спавнит
ребёнка, ждёт его через `wait4()`. Ребёнок запускается, пишет в
унаследованный fd 1, завершается. Планировщик переключается обратно на
родителя — и тот либо зависает навечно, либо падает в page fault по
случайному мусорному адресу (`#PF`, код ошибки `user+read+not-present`),
один в один при каждом прогоне.

### Причина

В ядре **два разных TSS** (Task State Segment — структура, в которой
процессор хранит, в частности, адрес стека для перехода из ring3 в
ring0 при прерывании/syscall'е — поле `RSP0`):

1. `boot/boot.asm` строит свой `tss64` и реально загружает его
   инструкцией `ltr` при старте. **Это единственный TSS, который
   когда-либо видит процессор.**
2. `kernel/gdt.c` строит **совершенно отдельную** структуру
   `tss_entry` и функцию `set_kernel_stack()`, которая писала RSP0
   именно туда. Но `gdt.c`'шный `init()`, который грузил бы этот TSS
   через `ltr`, **никогда не вызывается** (как и его GDT — тоже мёртвый
   код, реальная GDT тоже из `boot.asm`, это уже было известно раньше).

Итог: `activate_process()` при каждом переключении процесса честно
вызывал `set_kernel_stack(proc->kernel_stack)`, надеясь дать новому
процессу его персональный 8KB-стек под `kernel_stacks[idx]`. Но писал
он в структуру, которую процессор никогда не читает. **Реальный RSP0
был зашит намертво один раз при загрузке (ещё в `boot.asm`) и всегда
указывал на один и тот же временный 16KB загрузочный стек
(`stack_top`), общий для вообще всех процессов, сколько бы их ни
было.**

Пока в системе жил только один процесс — это было незаметно: один
процесс спокойно "гонял туда-сюда" по этому общему стеку, он же был
только у него. Баг молчал ровно до первого момента, когда **второй**
процесс реально делает свой собственный syscall, пока первый
подвешен где-то посередине своего. Именно это и происходит в тесте:
пока родитель висит в цикле `wait4()`, ребёнок запускается и делает
**свои собственные** `write`/`exit` — которые, по той же причине,
тоже лезут на тот же самый общий стек, прямо поверх ещё не прочитанного
сохранённого состояния родителя. К моменту, когда планировщик
пытается восстановить родителя — там уже не его данные, а огрызки от
ребёнка (в дампе отладки это было прекрасно видно: "восстановленный"
адрес возврата содержал буквально код возврата ребёнка — 42 — в одной
из половин 64-битного слова).

### Исправление

`kernel/gdt.c`, `set_kernel_stack()` теперь пишет прямо в настоящий,
реально загруженный `tss64` (экспортирован из `boot.asm` как
`global tss64`), по оффсету `+4`, где в x86_64 TSS и лежит `RSP0`
(первые 4 байта — зарезервированы):

```c
extern uint8_t tss64[];
void set_kernel_stack(uint64_t stack) {
    tss_entry.rsp0 = stack;              /* оставил для consistency */
    *(uint64_t *)(tss64 + 4) = stack;    /* а это реально работает */
}
```

Заодно в `kernel/onion.c`, рядом с уже существующим (из прошлого
раунда) `vmm_switch_pml4(init_proc->pml4)` для самого первого запуска
init, добавил аналогичный явный `set_kernel_stack(init_proc->kernel_stack)`
— раньше init точно так же жил на общем загрузочном стеке вплоть до
первого настоящего переключения, просто это не успевало вскрыться,
пока не появлялся второй живой процесс.

Проверено: 3+ отдельных прогона в QEMU с диском, каждый раз полный
трейс `init: start → child: hello → child: exiting 42 → init: reaped
child, status=42` — ни одного зависания, ни одного `#PF`.

## Файловая система: что было не так раньше

Ты упоминал, что раньше была "какая-то херня с файловой системой".
Разобрал — там было (минимум) две независимые проблемы, не связанные
с багом планировщика выше:

1. **Не было `mkfs`.** В проекте вообще не было инструмента, который
   создавал бы корректно отформатированный образ диска под `xv6fs`.
   Даже если диск физически подключить к QEMU — на нём просто не было
   правильной суперблочной структуры, которую `xv6fs` ожидает видеть.
   Старый `makefile` собирал какой-то `fs.img` как multiboot-модуль —
   но ни один кусок кода ядра его так не читает: `xv6fs` монтируется
   только с настоящего AHCI-диска (`kernel/onion.c`:
   `ahci_init()` → `ahci_get_device(0)`), multiboot-модуль 0 — это
   всегда ELF самого init'а, а не файловой системы. То есть тот
   `fs.img` был чистый мёртвый груз.

   Написал `tools/mkfs.c` — хостовая (не freestanding) C-программа,
   повторяющая алгоритм классического `mkfs.c` из xv6, но под наш
   формат инода (`addrs[NDIRECT+2]` — прямые блоки + один уровень
   косвенной адресации + два уровня, у исходного xv6 только один
   уровень косвенной). Собирается и гоняется на хосте при сборке
   (`make fs.img`), кладёт на диск корень, `/etc`, `/bin`, `/root`,
   `/README` и (в тестовой сборке) `/bin/child`.

2. **Баг в AHCI-драйвере (`kernel/ahci/onahci.c`).** Указатели на
   MMIO-регистры контроллера (`hba_mem_t*`, `hba_port_t*`) не были
   помечены `volatile`. Это не стилистическая придирка: регистр
   меняется самим железом асинхронно, "за спиной" компилятора. Без
   `volatile` компилятор на `-O2` имел полное право один раз прочитать
   `port->ci` в регистр и потом просто бесконечно крутиться по этому
   закэшированному значению — визуально это выглядит как "диск
   завис", хотя железо давно всё сделало. Хуже того — иногда это
   "работало" чисто по везению оптимизатора (если рядом был код,
   из-за которого компилятор не был уверен, что `port->ci` точно не
   меняется, и перечитывал его) — то есть баг был не детерминирован
   между сборками/версиями компилятора, именно такой "то работает, то
   нет" эффект.

   Поправлено: все указатели на регистры — `volatile`. Плюс у циклов
   опроса регистров (`ahci_port_stop/start`, ожидание завершения
   команды в `ahci_do_rw`) добавлен нормальный таймаут
   (`AHCI_IO_TIMEOUT`), который возвращает настоящую ошибку ввода-
   вывода вместо немого бесконечного зависания или молчаливого
   "как-нибудь само пройдёт".

Обе проблемы проверены по отдельности и вместе: несколько чистых
прогонов QEMU с реально подключенным AHCI-диском, каждый раз корректно
читается `/README` (252 байта), ни одного таймаута/зависания.

## Защита от чужих дисков: проверка magic (добавлено позже)

**Проблема.** `xv6fs_iinit()` читал суперблок и не проверял `magic`. Ядро
монтировало *первый найденный AHCI-диск* как xv6fs и сразу писало
(`create_default_dirs()`). На реальном ноуте это внутренний SATA-диск с
чужой ФС: мусорный "суперблок" -> `balloc()` пишет в случайные места.

**Что сделано:**
- `kernel/xv6fs/fs.c`: глобальный `xv6fs_mounted`; `xv6fs_iinit()` теперь
  возвращает `int` и при `sb.magic != XV6_MAGIC` возвращает -1, ничего не
  монтируя.
- `balloc()` и `ialloc()` (через них идут все аллоцирующие записи) делают
  `panic()`, если `xv6fs_mounted == 0` — вторая линия обороны.
- `xv6fs_full_init()` возвращает `int`; `onion.c` при -1 пишет
  "magic mismatch -- NOT mounting, disk left untouched" и не вызывает
  `create_default_dirs()` / чтение README. Ядро грузится дальше без ФС.

**Проверено в QEMU:** диск из 4MB случайных байт -> md5 до и после запуска
совпадает; единственное обращение — безвредный READ по мусорному LBA
(теперь в логе видно READ/WRITE и LBA). Нормальный образ монтируется как
раньше.

**Попутно исправлено:** `open(O_CREAT|O_TRUNC)` на уже существующем файле
не обрезал его (обрезка была только в ветке без O_CREAT). Блоки при
обрезке не освобождаются (`itrunc` static в fs.c) — утечка, пока нет
экспортированного truncate.

**Всё ещё не безопасно на реальном ноуте с данными:** чтения диска всё
равно происходят, и ядро — хобби-ядро. Сначала QEMU, потом диск, который
не жалко.

## API-справочник

### Syscalls (`int 0x80`, `rax`=номер, `rdi/rsi/rdx`=args 1/2/3, возврат в `rax`)

| № | Имя | Сигнатура | Файл |
|---|-----|-----------|------|
| 0 | read | `read(fd, buf, len)` | kernel/syscall.c |
| 1 | write | `write(fd, buf, len)` | kernel/syscall.c |
| 2 | open | `open(path, flags)` | kernel/syscall.c |
| 3 | close | `close(fd)` | kernel/syscall.c |
| 33 | dup2 | `dup2(oldfd, newfd)` | kernel/syscall.c |
| 59 | execve | `execve(path)` — упрощённо, без argv/envp отдельным массивом (argv передаётся через `arg2/arg3`, см. `spawn_from_xv6fs`) | kernel/syscall.c |
| 60 | exit | `exit(code)` | kernel/syscall.c → `exit_current_process()` |
| 61 | wait4 | `wait4(pid, *status, options, rusage)` — `pid/options/rusage` игнорируются | kernel/syscall.c |

fd 0/1/2 по умолчанию — клавиатура/экран (`kgetc`/`kprintn`), если не
были перенаправлены через `open`+`dup2`. fd 3..15 — обычные файлы на
xv6fs.

### Функции процессов (`kernel/process.h`, `kernel/process.c`)

```c
void       scheduler_init(void);
process_t *get_current_process(void);
process_t *get_process_by_pid(uint32_t pid);
int        create_process(uint64_t entry_point);   /* -1 при ошибке, иначе pid */
void       set_process_entry(process_t *proc, uint64_t entry_point);
void       set_process_argv(process_t *proc, uint64_t argc, uint64_t argv_ptr);
void       exit_current_process(int exit_code);     /* не возвращается */
uint64_t   schedule(uint64_t current_esp);           /* вызывается из timer IRQ / не вызывать руками */
```

`process_t` (ключевые поля):

```c
uint32_t pid, ppid;
int      exit_code;
process_state_t state;   /* READY / RUNNING / ZOMBIE / TERMINATED */
uint64_t *pml4;           /* своя таблица страниц */
struct { void *ip; uint32_t offset; int flags; } ofiles[16];
```

### Константы (`kernel/process.h`)

```c
#define MAX_PROCESSES     8      /* фиксированный размер processes[] */
#define KERNEL_STACK_SIZE 8192   /* на процесс */
#define USER_STACK_SIZE   16384  /* на процесс */
```

Поднять `MAX_PROCESSES` — просто число в define, массивы статические,
больше процессов — больше BSS, ничего хитрого.

## Что сознательно НЕ делал в этом раунде

- **`fork()`** — пункт 5 из плана, явно отложен. Модель
  "execve как единственный способ породить процесс" уже покрывает
  "init спавнит демона", больше пока не нужно.
- **Блокирующий `wait()`** — нужен новый `PROCESS_STATE_WAITING` +
  адресное пробуждение в `schedule()`. Сейчас `wait4()` — не блокирующий,
  требует поллинга. Если всплывёт реальная необходимость (не просто
  "красивее") — отдельная заметная задача, не на 5 минут.
- **Усыновление осиротевших zombie init'ом** — см. ограничение в
  разделе про `wait4()` выше.

## wait4 (блокирующий), fork, kernel/syscalls/

* `kernel/syscalls/` — новая таблица системных вызовов по номерам Linux
  (`numbers.h`, `dispatch.c`). `syscalls.asm` теперь вызывает
  `syscall_dispatch(regs)`, который возвращает esp для продолжения; всё, чего
  нет в таблице, идёт в старый `syscall_handler` (переносим по одному).
  Сюда же потом встанет вход через MSR (syscall/sysret) — тело обработчиков
  не изменится.
* `wait4(pid, *status, options)`: Linux-семантика (-ECHILD=-10, WNOHANG=1,
  status = (код & 0xFF) << 8). Блокировка: процесс помечается WAITING, RIP
  откатывается на 2 байта (на саму инструкцию int 0x80), rax=61; выход
  потомка будит родителя, тот повторяет вызов и находит зомби.
* `fork()` (57): `process_fork` копирует 20-словный фрейм (rax=0 у потомка),
  `vmm_copy_user_space` копирует все страницы с PAGE_OWNED; fd дублируются
  через idup. Сироты переподвешиваются к pid 1.
* Найденный баг: PDE ядра указывали на общие 4К-таблицы ядра; reap их
  освобождал (ядро теряло свои страницы → #PF в create_user_pml4). Теперь
  `kpde()` пропускает общие PDE и в copy, и в free.
* `process_reap` отпускает inode открытых файлов (iput).
* Тест (user.c, QEMU): wait4 по pid, -ECHILD, fork с изоляцией памяти,
  WNOHANG, осиротевший внук — всё проходит.

## Вход через `syscall` (MSR) и память процесса (mmap)

### MSR-вход (`kernel/syscalls/msr.c`, `entry.asm`)
* `msr_syscall_init()` (вызывается из `onion.c` после `set_kernel_stack`):
  EFER.SCE=1, STAR (ядро CS=0x08, база sysret 0x10 — совпадает с `gdt64`
  из boot.asm), LSTAR=`syscall_entry`, FMASK=IF|DF|TF.
* `syscall` не переключает стек: `entry.asm` кладёт пользовательский rsp в
  глобальную переменную, берёт стек ядра из `TSS.RSP0` и строит ТОЧНО такой
  же 20-словный кадр, как `int 0x80`. Поэтому диспетчер, блокировка
  `wait4` (откат RIP на 2 байта — обе инструкции по 2 байта) и `fork` не
  менялись. Выход всегда через `iretq`, не `sysretq` (sysretq не умеет
  возобновлять кадр, сохранённый таймером).
* Пользовательская обёртка: `syscall` с clobber `rcx`, `r11`; четвёртый
  аргумент в `r10`, пятый `r8`, шестой `r9` (кадр: r10=regs[5], r8=[7],
  r9=[6]). `int 0x80` продолжает работать.

### Память (`kernel/syscalls/sys_mem.c`, `vmm.c`)
* Таблицы страниц — источник истины. Страницы процесса: PTE с PAGE_OWNED;
  PROT_NONE = PTE без PRESENT с битом PAGE_PROTNONE (бит 10), страница
  остаётся за процессом. fork копирует, exit освобождает именно их.
* `process_t.vmas[32]` хранит только диапазоны, выданные mmap (для поиска
  дыры first-fit и для munmap).
* Вызовы: mmap(9), mprotect(10), munmap(11), madvise(28, заглушка),
  brk(12) теперь освобождает страницы при уменьшении и зануляет новые.
  Ошибки — `-errno` в rax, как в Linux.
* Диапазоны: автоматическое размещение 16 ТБ…96 ТБ; MAP_FIXED только в
  [4 ГБ, 0x7000_0000_0000) — ниже 4 ГБ таблицы страниц общие с
  identity-map ядра, и туда писать нельзя.
* Ограничения: страницы выделяются сразу (нет ленивого выделения по #PF);
  файловый mmap копируется при вызове и всегда приватный (MAP_SHARED не
  пишет обратно в файл); PROT_EXEC принимается, но не применяется (NXE
  выключен); mremap нет.
* Новые функции vmm: `vmm_pte`, `vmm_free_page`, `vmm_protect_page`.

### Сборка
* makefile теперь отслеживает зависимости от заголовков (`-MMD -MP`).
  Раньше после правки `process.h` часть объектов оставалась со старой
  раскладкой `process_t` и ядро вело себя странно (wait4 вдруг давал
  -ECHILD) — ловушка найдена именно так.

### Тесты (user.c, QEMU, всё проходит)
syscall и int 0x80 дают одинаковый результат; mmap зануляет и
сохраняет данные; munmap + повторный mmap использует дыру; PROT_NONE и
обратно не теряют данные; mprotect по неотображённому диапазону даёт
-12; fork изолирует отображение; MAP_FIXED; файловый mmap совпадает с
read(); brk зануляет страницы после повторного роста; 300×2 МБ
mmap/munmap не течёт (при утечке не хватило бы 128 МБ ОЗУ).

## Настоящий execve, стартовый стек SysV, arch_prctl

### execve (59) — `kernel/syscalls/sys_exec.c`
* Теперь это настоящий Linux-execve: процесс сохраняет pid, родителя,
  открытые файлы и стек ядра, получает новое адресное пространство.
  Запуск программы — `fork` + `execve`. Старое поведение «создать нового
  потомка» осталось как нестандартный вызов 500 `notux_spawn`.
* Порядок гарантирует, что неудачный execve ничего не ломает: 1) path,
  argv, envp копируются из старого пространства в ядро (с проверкой, что
  страницы отображены — иначе -EFAULT, а не падение ядра); 2) ELF читается
  в буфер из `pmm_alloc_contig` (до 16 МБ, освобождается сразу) и
  проверяется; 3) новое пространство целиком строится заранее (сегменты,
  стек 128 КБ, argv/envp/auxv); 4) только потом переключается CR3, старое
  освобождается, сохранённый кадр переписывается (RIP, RSP, регистры = 0,
  rdi=argc, rsi=argv для старых программ).
* Стартовый стек (System V ABI, как ждёт musl crt1): `argc, argv[], NULL,
  envp[], NULL, auxv…`, rsp выровнен по 16. auxv: AT_PHDR, PHENT, PHNUM,
  PAGESZ, BASE(0), FLAGS, ENTRY, UID/EUID/GID/EGID, PLATFORM, CLKTCK,
  SECURE, RANDOM (16 байт из rdtsc), EXECFN. AT_PHDR нужен статическому
  musl, чтобы найти PT_TLS.
* Ограничения: PIE/ET_DYN не релоцируется (грузится по p_vaddr), нет
  PT_INTERP (нужны для .so — следующий этап), не больше 64 аргументов и
  32 КБ строк (-E2BIG), нет close-on-exec (все fd наследуются).

### arch_prctl (158) и мелочи
* `ARCH_SET_FS/GET_FS`: база FS хранится в `process_t.fs_base`, пишется в
  MSR IA32_FS_BASE (0xC0000100) и перезагружается при каждой смене процесса
  (`activate_process`); fork копирует, execve обнуляет. GS не поддержан
  (-EINVAL).
* `set_tid_address`, `gettid`, `exit_group`, `getuid/geteuid/getgid/getegid`
  (всегда 0).

### Другое
* `tools/mkfs`: дополнительные программы `name=file` → `/bin/name`.
* `pmm_alloc_contig / pmm_free_contig` — непрерывные физические страницы.
* ЛОВУШКА, найденная по пути: статический буфер ELF в `.bss` ядра нельзя
  увеличивать — при 1 МБ bss перекрыл место, куда GRUB положил модуль
  init, и процессы начали портить стек. Поэтому статический буфер остался
  256 КБ (его использует только `notux_spawn`), а execve берёт память из pmm.

### Тесты (QEMU)
argtest через fork+execve получает argc=3, argv/envp, auxv (PAGESZ=4096,
PHNUM>0, PHDR, ENTRY, RANDOM, EXECFN), rsp%16=0; execve несуществующего
файла возвращает -2, и процесс продолжает работать; два процесса с разными
FS-базами 40 млн итераций каждый (много переключений) всегда читают свой
`%fs:0`.

## Файловые вызовы Linux (шаг 1 к оболочке) — `kernel/syscalls/sys_fs.c`

Принцип: ядро реализует Linux-ABI «как есть», программы (musl и glibc)
не патчатся. Поэтому, кроме классических вызовов, есть и их `*at`-варианты,
которые использует glibc.

* `stat`(4), `fstat`(5), `lstat`(6), `newfstatat`(262, в т.ч.
  AT_EMPTY_PATH): структура `stat` в раскладке Linux x86_64 (144 байта).
  В xv6fs нет прав, владельцев и времени, поэтому: режим 0755 у всех,
  uid/gid 0, времена 0; fd 0–2 без перенаправления — символьное устройство.
* `access`(21), `faccessat`(269): проверяют существование.
* `getdents64`(217): записи Linux `linux_dirent64` из 16-байтных записей
  xv6fs, смещение fd = байтовая позиция в каталоге; `d_type` = DT_UNKNOWN.
* `chdir`(80) и `getcwd`(79): рабочий каталог теперь ОТДЕЛЬНЫЙ у каждого
  процесса (`process_t.cwd`, процесс держит ссылку на inode; fork берёт
  ещё одну, reap отпускает). Диспетчер перед каждым вызовом направляет
  «fake proc» xv6fs на cwd вызывающего. `getcwd` восстанавливает путь,
  идя по «..» и ища своё имя в родителе (xv6fs путь не хранит).
* `pread64`(17), `readlink`/`readlinkat`(89/267, всегда -EINVAL — ссылок
  нет), `umask`(95), `uname`(63, sysname "notux", release "6.1.0"),
  `getpgrp`/`getpgid`/`setpgid`/`setsid` (пока каждый процесс — своя
  группа).
* `openat`(257), `mkdirat`(258), `unlinkat`(263): пересылаются в старые
  обработчики, при относительном пути dirfd временно служит как cwd.
* `uaccess.c`: `copy_from_user`, `copy_to_user`, `strncpy_from_user` —
  проверяют страницы по таблицам процесса и возвращают -EFAULT вместо
  падения ядра. Новые вызовы используют только их.

Ограничения xv6fs, которые видны программам: имя файла не длиннее 14
символов, нет прав/времён/ссылок, размер файла до ~8 МБ.

Тест `tests/musl_fs.c` (musl, статически): opendir/readdir, stat,
chdir/getcwd (в том числе `..`), относительные пути, fopen/fgets, pread,
fstat, наследование cwd потомком после fork — 17 проверок, все проходят.

## xvsXfs: новая файловая система (этап 1 — формат и хостовые инструменты)

Решение: вместо латания xv6fs (блок 512 Б, имена по 14 символов, файл до
~8 МБ, нет прав и времён) — собственный формат на её основе: блок 4 КБ,
inode 512 Б, extents, имена до 255, mode/uid/gid/времена, симлинки, inline-
данные до 256 Б, crc32c метаданных, место под журнал. Полное описание —
`docs/XVSXFS.md`, структуры — `kernel/xvsxfs/xvsx_format.h`.

Сделано (всё на хосте, ядро пока не трогали):
* `tools/xvsx/xvsx_lib.c` — общая библиотека (блоки, карты, inode, extents
  с деревом глубины 0/1, каталоги переменной длины, inline, симлинки).
* `mkfs.xvsx`, `fsck.xvsx` (только чтение), `xvsx-dump`.
* `tests/xvsx_test.py` (`make xvsx-test`): 414 файлов разных размеров (0 Б …
  3 МБ, имя 255 символов, UTF-8, каталог на 400 записей = 2 блока),
  фрагментированный файл с деревом extents глубины 1 — и 13 намеренных
  порч (бит в inode / суперблоке / каталоге / узле extents / картах /
  журнале, обрезанный образ, подделанные `nlink`, `size` и двойное
  владение блоком с ВАЛИДНОЙ контрольной суммой): fsck находит все.
  Итог 25/25.

Ошибка по дороге: размер области записей каталога сначала был 4084 — не
кратен 8, любая запись считалась битой. Хвост сделан 16 байт, область 4080.

Дальше: монтирование в ядре (только чтение) через тонкий слой VFS, затем

## Шаг A: таблица открытых файлов (fd-слой с Linux-семантикой)

Раньше у процесса было `ofiles[16]` {inode, offset, flags}: dup/fork копировали
смещение, а не делили его, консоль определялась по «fd 0..2 без inode».
Теперь:

- `kernel/syscalls/kfile.h`, `sys_file.c`: глобальный пул `struct kfile`
  (256 объектов: refs, type = FT_CONSOLE|FT_INODE, flags, 64-битное смещение,
  inode). Дескриптор — `process_t.fds[64]` + `fd_flags[64]` (FD_CLOEXEC).
- dup/dup2/dup3/fcntl/fork/execve делят объект → смещение и O_APPEND общие,
  как в POSIX. execve закрывает CLOEXEC-дескрипторы (`fdt_close_cloexec`).
- 0/1/2 у нового процесса — консольные объекты (раньше «пустой слот»).
- read/write идут через bounce-буфер и `copy_{to,from}_user` (EFAULT вместо
  падения ядра); write в O_RDONLY / read из O_WRONLY → EBADF, каталог → EISDIR.
- open/openat: Linux-флаги (O_CREAT/EXCL/TRUNC/APPEND/DIRECTORY/CLOEXEC),
  errno: ENOENT, EEXIST, ENOTDIR, EISDIR, EMFILE, ENFILE. lseek на консоли → ESPIPE.
- Из `kernel/syscall.c` удалены старые ветки read/write/open/close/lseek/dup/dup2
  и мёртвый `notux_spawn` (500) вместе с `spawn_from_xv6fs`.
- Консольный read по-прежнему неблокирующий (вернёт 0) — это шаг D (tty).
- Известное: O_TRUNC только обнуляет size (блоки текут, нет itrunc).
- Тест `tests/musl_fd.c` (36 проверок): общие смещения dup/fork, запись через два
  дескриптора, O_APPEND, errno, F_DUPFD/F_GETFD/F_SETFD, dup3, CLOEXEC через
  execve, лимит дескрипторов. Все старые тесты в QEMU зелёные.

## Шаг B: pipe/pipe2 и общий механизм сна

- `sleep_on(regs, nr, chan)` / `wakeup(chan)` (process.c): обобщение приёма из
  wait4. Процесс встаёт на «канал» (любой указатель), RIP откатывается на
  2-байтную инструкцию syscall/int 0x80, rax = номер вызова; после `wakeup`
  вызов просто выполняется заново. wait4 переведён на него (канал = процесс-родитель).
  Прерывания в syscall выключены, поэтому «проверил → заснул» атомарно.
- `sys_pipe.c`: pipe/pipe2 (O_CLOEXEC, O_NONBLOCK). Буфер 4 КБ — отдельная страница
  из pmm (не .bss), два объекта FT_PIPE_R/FT_PIPE_W. read: пусто+нет писателей → 0 (EOF),
  O_NONBLOCK → EAGAIN, иначе сон. write: нет читателей → EPIPE (SIGPIPE
  появится вместе с сигналами); запись ≤4096 атомарна (ждёт места целиком),
  больше — кусками, может вернуть короткий результат.
- read/write возвращают внутренний `E_BLOCK`; readv/writev (vec_io) умеют
  засыпать, если ещё ничего не передано.
- **exit закрывает дескрипторы сразу**, а не при wait: иначе читатель пайпа не
  увидит EOF, пока родитель не сделает wait4 (классический дедлок в `a | b`).
- fstat: консоль = S_IFCHR, пайп = S_IFIFO; pread на пайпе → ESPIPE; getdents на
  не-каталоге → ENOTDIR.
- MAX_PROCESSES 8 → 32. Побочный урок: статический массив ядерных стеков
  (32×8 КБ) в .bss сломал загрузку (процессы падали с #PF в цикле) — как и раньше
  с большим буфером ELF: GRUB кладёт модуль сразу за ядром. Ядерные стеки
  теперь выделяются из pmm при первом использовании слота.
- Тесты в `tests/musl_fd.c`: обмен через пайп, EBADF на «не тот» конец, ESPIPE,
  fstat FIFO, EOF, EPIPE, O_NONBLOCK→EAGAIN, блокирующий read (писатель пишет
  позже), 100 000 байт через 4 КБ буфер (писатель блокируется), dup2 пайпа на stdout
  дочернего execve-процесса и чтение его вывода.
- Известное: на пайп нет poll/select (шаг E); заблокированный процесс не
  просыпается по сигналу (сигналов ещё нет); пайп-буфер не растёт.

## Шаг E: время, сон по таймеру, poll/select

- `kernel/ktime.c`: счётчик тиков PIT (100 Гц; `timer_tick()` вызывается из
  `timer.asm` перед `schedule`), монотонные часы, настоящее время из RTC (CMOS,
  читается лениво один раз, BCD/12-часовой режим учтены) + тики. Разрешение всего — 10 мс.
- `sleep_until(regs, nr, chan, wake_tick)`: сон с таймаутом; `timer_tick` будит
  просроченных. Дедлайн хранится в процессе (`tmo_deadline`), потому что
  заблокированный вызов перезапускается с начала после каждого пробуждения.
- **Исправлен простой планировщика**: раньше, если все процессы спали, `schedule`
  зависал в `hlt`-цикле и не мог переключиться на проснувшегося по таймеру
  (будить было некому — всегда будил другой процесс). Теперь флаг `idle_active`
  сбрасывается при выборе процесса, и вложенное прерывание таймера переключается
  на проснувшегося.
- Вызовы: clock_gettime/getres (REALTIME, MONOTONIC, *_COARSE, BOOTTIME; CPUTIME пока
  = стенные часы), gettimeofday, time, times (поля tms нулевые, возврат — тики),
  nanosleep, clock_nanosleep (включая TIMER_ABSTIME), sched_yield, poll, ppoll,
  select, pselect6.
- poll/select: готовность через `kfd_poll`: пайпы (IN/OUT/HUP/ERR), консоль (клавиатура —
  опрос раз в тик, будильника у неё нет), обычные файлы всегда готовы, неверный fd —
  POLLNVAL / EBADF. Спящие на poll/select ждут на `poll_chan`, пайп будит его
  при любом изменении. При таймауте select очищает множества, как Linux.
- Известное: sigmask у ppoll/pselect6 игнорируется (сигналов нет); CPU-время
  процесса не считается; таймер — один PIT, без LAPIC/TSC.
- Тест `tests/musl_time.c` (33 проверки): часы, RTC, nanosleep/usleep/sleep(1) с
  замером, poll с таймаутом/блокировкой/HUP, select, ppoll, ошибки. Все старые тесты зелёные.

## musl внутри проекта, /bin/init

- `musl/` — готовый musl (libc.a, libm.a, crt1/crti/crtn.o, заголовки; 3.7 МБ, MIT):
  программы собираются обычным gcc (`-static -no-pie -nostdlib crt1.o crti.o prog libc.a libgcc.a crtn.o`),
  `musl-gcc`/`musl-tools` больше не нужны (удобно на Gentoo и др.). Правила в makefile:
  `musl_%.elf` из `tests/musl_%.c`, `init.elf` из `init.c`; список `MUSL_PROGS`.
- `init.c` — пример настоящего init на musl (печатает, делает fork+execve `/bin/child`,
  не выходит, собирает осиротевших). Первая ступень (`user.c`, модуль GRUB) может
  просто `execve("/bin/init")`: проверено, на экране видны `hello from musl init`
  и вывод child. init из модуля напрямую musl-программой быть не может: у него нет
  SysV-стека с auxv (его строит только execve).

## IO-вызовы для утилит (rename/link/rmdir/truncate/statfs/…)

Список взят из `strace` статического mksh + то, что нужно ls/cp/rm/mv/mkdir.
- Каталоги: mkdir/mkdirat, rmdir, unlink/unlinkat (AT_REMOVEDIR) с честными errno
  (EEXIST, ENOENT, ENOTDIR, EISDIR, ENOTEMPTY, EINVAL для `.`), новая

- link/linkat (жёсткие ссылки, каталоги → EPERM), symlink/mknod → EPERM (в xv6fs их нет).

## Сигналы: настоящая доставка (шаг C)

- `signal_post(p, sig)` только ставит бит в `sigpending` (SIG_IGN и «игнор по умолчанию» отбрасываются; SIGKILL убивает сразу) и будит спящего, если сигнал не заблокирован.
- `signal_check(frame)` вызывается на каждом возврате в user-mode (конец `syscall_dispatch` и `timer.asm`): берёт младший ожидающий незаблокированный сигнал; SIG_DFL → завершение процесса, иначе на пользовательском стеке строится Linux-совместимый `rt_sigframe` (siginfo + ucontext + fxsave), обработчик стартует с `rdi/rsi/rdx = sig/info/uc`, возврат через `restorer` → `rt_sigreturn` (nr 15).
- Прерванный сон: `sleep_on` помечает кадр (`restart_frame`). При доставке: `-EINTR` либо рестарт вызова при `SA_RESTART` (nanosleep/poll/select/pause/sigsuspend никогда не рестартуют). `wait4`, разбуженный выходом ребёнка, сначала отдаёт зомби, потом запускает обработчик SIGCHLD.
- `rt_sigsuspend` временно меняет маску (`saved_mask`, `sigsusp`), после обработчика маска возвращается.
- SIGCHLD при выходе ребёнка, SIGPIPE при записи в pipe без читателей, SIGALRM от `alarm`/`setitimer(ITIMER_REAL)` (тик 100 Гц).
- Ошибки пользователя (#PF/#GP/#UD/#DE…) → SIGSEGV/SIGILL/SIGFPE/SIGBUS (действие по умолчанию, процесс умирает, wait4 видит сигнал). Раньше #PF зацикливался.
- FPU/SSE: ядро собирается с `-mgeneral-regs-only`, состояние FXSAVE хранится по процессу (страницы из pmm), переключается в `schedule()`; fork копирует, execve сбрасывает.
- Исправлен баг простоя: `idle_active` не сбрасывался, когда единственный процесс просыпался сам по таймеру → следующий сон превращался в бесконечный рестарт.
- Тесты: `tests/musl_sig2.c` (обработчики, маски, EINTR/SA_RESTART, SIGCHLD+sigsuspend, SIGPIPE, SIGSEGV, FPU). `mksh -c` со скриптом (подстановка команд, циклы, pipe) даёт exit 7.
- Отладка: `make iso TRACE=1` печатает каждый syscall в serial; неизвестные номера печатают `ENOSYS nr=…`. Необязательный `mksh.elf` в корне проекта кладётся в `/bin/mksh` и запускается тестом 19.
- Не сделано: SA_ONSTACK/sigaltstack, SIGSTOP/SIGCONT (job control), доставка обработчика при user-fault (только действие по умолчанию).

## /proc (виртуальная ФС)

- `kernel/syscalls/procfs.c`: файлы генерируются ядром при `open` (снимок, как в Linux), на диске ничего нет. Только абсолютные пути `/proc/...`.
- Есть: `cpuinfo` (cpuid), `meminfo`, `uptime`, `version`, `mounts`, `loadavg`, `stat`, `filesystems`, `/proc/<pid>/{status,stat,cmdline}`, `/proc/self`. Каталоги читаются через `getdents64`.
- Новый тип открытого файла `FT_PROC` (`read`, `lseek`, `fstat`, `stat`, `access`, `getdents64` его понимают). Запись и создание → `EACCES`.
- В `process_t` появилось `comm` (имя исполняемого, ставится в `execve`) — его показывает `/proc/<pid>/status`.
- `meminfo`: MemTotal = диапазон, которым управляет pmm (128 МБ), не весь RAM.
- Тест: `tests/musl_proc.c` (31 проверка).

### Найденный латентный баг (почему «рос bss — ломалась загрузка»)

Программы линкуются на 0x400000. Когда процесс мапит их, 2-МБ identity-запись ядра для 0x400000–0x5FFFFF превращается в приватную таблицу страниц процесса, и ядро больше не может писать в *физические* страницы из этого диапазона через identity-карту (запись попадает в страницы пользователя). pmm выдаёт страницы с нижних адресов, поэтому, как только свободная низкая память кончалась (чем больше ядро/bss, тем раньше), ядро портило код и данные пользователя (`#UD`, прыжки в rodata). Исправление: `pmm_reserve_region(0x400000, 0x1000000)` — эти физические страницы не выдаются. Долгосрочно: прямая карта физической памяти в верхней половине адресов.

## sbase (ступень 4) и находка про pmm

`tools/files/sbase_test.sh` (≈55 проверок: cat/wc/sort/uniq/cut/grep/sed/cp/mv/ln/find/tar/xargs/od/sha256/md5…)
запускается из интерактивного mksh: `mksh /mnt/sbase_test.sh` → все `ok`. Сборка: tools/ladder/04-sbase.sh,
образ с утилитами: tools/mkext2test.sh (16M, /bin + sbase_test.sh).

Находка: `mksh` из mksh падал. Корневая причина: у init (`user.elf`) есть PT_LOAD по 0x3ff000, а PDE
для 0x200000–0x3fffff после AHCI указывает на общую с ядром 4K-таблицу. `vmm_map_page` писал пользовательский
PTE прямо в эту общую таблицу и затирал identity-запись ядра для 0x3ff000 (она начинала вести на другую
физическую страницу), так что ядро и процесс видели разные страницы. Исправлено: `vmm_map_page` для
не-ядерного pml4 сначала копирует общую PT в приватную (copy-on-write таблицы). Резерв pmm остался как был
(0x400000–0x1000000); обходной путь с 0x200000 не нужен.

## Память: пробелы перед .so

- `mremap` (уменьшение, рост на месте, перенос с `MREMAP_MAYMOVE` перепривязкой PTE без копирования; `MREMAP_FIXED` → EINVAL).
- `msync`/`mlock`/`munlock`/`mlockall`/`munlockall` — успешные заглушки, `mincore` — все свои страницы резидентны.
- `MAP_FIXED_NOREPLACE` (EEXIST), `ENODEV` при mmap не-обычного файла.
- Таблица VMA 32→512 записей, соседние диапазоны склеиваются (загрузчик, который кладёт сегменты вплотную, не съедает таблицу).
- pmm: управляемая память 128 МиБ → 1 ГиБ, реальный размер берётся из multiboot `mem_upper` (`pmm_set_limit`),
  `/proc/meminfo` показывает его; выделение стартует с подсказки «первая свободная», а не с нуля.
- Тест `musl_mm` (≈50 проверок: рост/перенос/сжатие, fixed-сегменты поверх резерва как у ld.so, файловый mmap со смещением,
  200 разрозненных отображений, malloc/realloc больших блоков, fork). Прогон: `musl_mm exit (expect 0)=0`.
- Остаётся: `MAP_SHARED` не пишет обратно в файл и не разделяется между fork (нужно для Wayland `wl_shm`), `PROT_EXEC` не
  принуждается (NXE выключен), нет demand paging.

## Динамическая линковка (.so): ступень 46

Как устроено (ядро — свой код по спецификации ELF/psABI; загрузчик — `ld-musl` из musl, MIT):
- `execve` понимает `ET_DYN`: основная программа ставится по базе 0x40_0000_0000 (256 ГиБ), интерпретатор из
  `PT_INTERP` — по 0x80_0000_0000 (512 ГиБ). Обе базы выше 4 ГиБ и ниже пула mmap (16 ТиБ), поэтому автоматический
  mmap и куча на них не попадают. Для статического PIE (ET_DYN без интерпретатора) стартует сама программа (`rcrt1`).
- Стек: `AT_PHDR`/`AT_PHENT`/`AT_PHNUM` (с учётом базы), `AT_ENTRY` программы, `AT_BASE` интерпретатора, `AT_RANDOM`, `AT_EXECFN`...
  Старт на точке входа интерпретатора. Загрузка сегментов — `load_elf_bias()` (смещение к `p_vaddr`).
- `/lib` — временный bind: каталог `/lib` на xv6fs показывает каталог `/lib` второго диска (ext2). Причина: имя
  `ld-musl-x86_64.so.1` длиннее 14 символов, а на xv6fs их нет. Известное ограничение: `/mnt/lib/..` даёт `/`, а не `/mnt`.
  Исчезнет, когда корень переедет на ext2.
- musl: `libc.so` Debian (MIT) копируется на диск как `/lib/ld-musl-x86_64.so.1` (+ симлинк `libc.musl-x86_64.so.1`);
  в `musl/lib` добавлены `libc.so`, `Scrt1.o`, `rcrt1.o`. `tools/mkext2test.sh` кладёт их и `libfoo.so` в образ.
- Тесты: `spie_hello` (static-pie), `dyn_hello` (PT_INTERP, libc.so), `dyn_lnk` (DT_NEEDED libfoo.so: данные, RELATIVE-релокации,
  конструктор, TLS, обратные вызовы в программу, слабые символы), `dyn_dl` (`dlopen`/`dlsym`/`dlclose`, поиск по пути,
  `dlopen(NULL)`, TLS загруженной библиотеки). Все зелёные; `openat` уже работал.
- Ещё нет: `MAP_SHARED` между процессами, `PT_GNU_STACK`/NX, `vDSO`, потоки (`clone`), переменные `LD_*` специфичные для glibc.

## Корень на ext2 (один диск) и tcc

- Старт: `xv6fs_full_init(disk0)`; если сигнатура не xv6fs, но на диске 0 валидный ext2 — `ext2_set_root_mode(1)`:
  ext2 становится `/`. `namex` берёт корень через `fs_rootdir()` (ext2 inode 2 вместо xv6fs 1), `..` на корне ext2 остаётся
  в корне (переход в точку монтирования только когда ext2 смонтирован на /mnt), `getcwd` заканчивается на корне, `/proc/mounts`
  показывает ext2. Режим «xv6fs корень + ext2 на /mnt» остаётся (диск 0 = xv6fs). Костыль bind `/lib` нужен только в нём.
- `statfs`/`fstatfs` для ext2 возвращают настоящие значения (`0xEF53`, размер блока, 255); `xv6fs_truncate` больше не зависит
  от xv6fs-монтирования для ext2-инодов. Добавлен `membarrier` (QUERY/GLOBAL), его вызывает musl при `dlopen`.
- Образ: `tools/mkext2root.sh` (`make ext2root.img`, `make ext2root-tests.img`): mke2fs -d из подготовленного каталога
  (FHS-каталоги, `/bin`, `/etc`, `/lib` с ld-musl, `/usr` с tcc, фикстуры ext2 в `/mnt`), `/dev/*` через debugfs `mknod`.
- Тесты `musl_io`/`musl_ext2w` определяют тип корня (14-символьные имена и EXDEV только на xv6fs).
- tcc (`tools/ladder/31-tcc.sh`, LGPL, внешний бинарник): динамический (через `tools/ladder/mccdyn`, иначе `-run` не работает —
  статический musl не умеет `dlopen`), `libtcc1.a` и `runmain.o` собираются свежим tcc против заголовков musl.

## OpenRC (BusyBox init → OpenRC → сервис)

- Цель: запустить OpenRC не как `user.elf`, а как то, что запускает init. Первый процесс (`user.c`) при наличии `/etc/inittab`
  делает `execve("/sbin/init")` и становится PID 1 (BusyBox init); тот выполняет `openrc sysinit/boot/default`, держит `mksh` через respawn.
- Ядро: `clone` (56, и `vfork` 58) как fork-копия — достаточно для `posix_spawn` musl (`CLONE_VM|CLONE_VFORK`: родитель ждёт CLOEXEC-pipe);
  `CLONE_THREAD` и пространства имён отклоняются (`EINVAL`), стек потомка берётся из аргумента; `rt_sigtimedwait` (128) для цикла init;
  `mount` (165) принимает только tmpfs/proc/sysfs/devtmpfs/devpts/cgroup — это ЗАГЛУШКИ (каталог остаётся обычным каталогом на ext2),
  остальное `ENODEV`; `umount2` — no-op; `reboot` (169) — sync и выключение через порты ACPI QEMU; `socket` → `EAFNOSUPPORT`,
  `connect/sendto` → `ENOTSOCK` (нет сети; убирает шум syslog).
- Сборка: `PATH` теперь с `/sbin:/usr/sbin`. Находка в `mkext2root.sh`: `cp` sbase поверх симлинков на busybox затирал `/bin/busybox`
  (`cp --remove-destination`). Для notux набор runlevel'ов урезан (нет sysfs/devfs/cgroups), добавлен сервис `hello`
  (`tools/files/hello.initd`) и `passwd/group`. `INIT=1 make ext2root.img` кладёт `/etc/inittab`; тест: `tools/test_openrc.sh`.
- Проверено: загрузка → OpenRC запускает `hello` (`/tmp/hello.state` = started), `kill -TERM 1` → остановка сервисов → reboot → выключение QEMU.
  Остаётся: настоящие tmpfs/devtmpfs, `/proc/<pid>/`, `flock`, fifo на ext2, `/etc/fstab`, сеть.

## UEFI

- Ничего нативного писать не пришлось: `grub-mkrescue` с модулями `grub-efi-amd64-bin` делает гибридный ISO (BIOS + `/efi.img`),
  GRUB-EFI грузит то же Multiboot1-ядро. Проверено под OVMF (q35): serial, AHCI-диск, ext2-корень, mksh, экран.
- Экран: под UEFI нет портов Bochs VBE как гарантии, поэтому заголовок Multiboot просит у загрузчика линейный режим 800x600x32,
  а `onion.c` берёт адрес framebuffer из Multiboot-информации (бит 12, смещения 88..109, `vbe_from_bootloader`); если режим не тот
  (другой pitch/размер/не RGB) — прежний путь через порты Bochs. grub.cfg получил `insmod all_video`. Работает и в BIOS-режиме.
- Запуск: `tools/qemu_uefi.sh [диск]`. Не сделано: нативный `BOOTX64.EFI`, ACPI-таблицы из RSDP, GPT (на UEFI-дисках), framebuffer
  других размеров (консоль жёстко 800x600).
